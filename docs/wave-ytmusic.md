# Волна на YouTube Music: как движок устроен на самом деле

Ориентир для будущей прокачки «Волны». Всё, что помечено **проверено**, сверено по коду
на `HEAD = addb379`. Идеи из раздела 4 — **гипотезы**, их нельзя брать в работу без
снятия живого ответа InnerTube (см. раздел 5).

---

## 1. Реальная цепочка

| Шаг | Место | Что делает |
|---|---|---|
| Вход | `src/player/manager.rs:709` | `start_station("user:onyourwave", …)` — id станции Яндекса переиспользуется для обоих провайдеров (`manager.rs:183`, `1928–1930`) |
| Refill-гейт | `src/player/manager.rs:884–885` | `refill_needed()` (осталось `< 3`) **или** `remaining <= 3` → догрузка |
| Догрузка | `src/player/manager.rs:1012` `load_more_wave_tracks` | спавнит задачу, для `YouTubeMusic` уходит в свою ветку (`1030–1052`) и **раньше**, чем используются mood/lang/character |
| Сеть | `src/api/ytmusic/mod.rs:1362–1463` `get_station_tracks` | continuation-режим либо seed-запрос + аварийный фолбэк |
| Парсер | `src/api/ytmusic/parser/radio.rs:73` `parse_radio_batch` | `playlistPanelVideoRenderer` → `Track`, затем `find_continuation_token` |
| Пост-фильтр | `src/player/wave_engine.rs:83` `filter_candidates` | история 100 треков (`MAX_RECENT_HISTORY`, строка 6), `is_clean_music_track`, дедуп по `id` |
| Хвост очереди | — | `dedup_tracks(&state.queue, filtered)` + `QueueUpdated` |

Один и тот же батч проходит `is_clean_music_track` **дважды** (в парсере `radio.rs:76` и в
`wave_engine.rs:95`) — безвредно, но при правках фильтра помнить.

## 2. Детали до байта

**Разрешение seed** (`mod.rs:1382–1411`), первый подходящий вариант побеждает:

1. `track:<id>` / `seed:<id>` (префикс, либо подстрока);
2. голая строка из 11 символов, не начинающаяся с `UC` — уже `videoId`;
3. `artist:<id>` → `get_artist().popular_tracks[0]`, иначе `bgKxYnTEN5Y`;
4. всё остальное (`user:onyourwave`, `radio`, любая строка с `onyourwave`) →
   `last_seed` из памяти → первый трек из «Мне нравится» → `bgKxYnTEN5Y`.

**`last_seed` — не дрейфующий.** Он перезаписывается сразу после каждого seed-запроса
(`mod.rs:1415–1418`), поэтому сам по себе сид никогда не меняется: пока в `station_id`
не придут новые `track:`/`seed:`, волна тянет один и тот же автомикс.

**Запросы** (`WEB_REMIX`, `clientVersion 1.20240101.01.00`, `post_innertube("next", …)`):

```json
{"videoId": "<seed>", "playlistId": "RDAMVM<seed>"}
{"continuation": "<token>"}
```

`RDAMVM` — официальный префикс трек-радио YT Music (проверено: `mod.rs:1424`, `1437`).

**Аварийный фолбэк** (`mod.rs:1428–1451`): если по сиду вернулось 0 треков —
повтор с `bgKxYnTEN5Y`, и при успехе `last_seed` перезаписывается на него же.
То есть один пустой ответ навсегда переводит волну на хардкод-сид.

**Continuation-токены.** `find_continuation_token` (`radio.rs:26–71`) смотрит четыре формы
по порядку рекурсивного обхода: `nextContinuationData.continuation`,
`nextRadioContinuationData.continuation`, `continuationCommand.token`,
`continuationItemRenderer.continuationEndpoint.continuationCommand.token`.
Пустой токен уезжает в `StationBatch.batch_id` как `String::default()`, а менеджер трактует
пустую строку как `None` (`manager.rs:1041`).

**Фильтр мусора** (`src/api/ytmusic/parser/track.rs:6–47`): не трек, если
длительность известна и лежит вне `30_000..=1_200_000` мс (30 с – 20 мин), **или** в
названии/артистах встречается слово из `MUSIC_STOP_WORDS` («подкаст», «выпуск #», «эпизод »,
«интервью», «стрим», «реакция » и т.д.). Отдельного признака «это подкаст» нет — только
стоп-слова, поэтому чистый подкаст без маркеров в названии пройдёт.

## 3. Что из присланного описания неточно

- `get_station_tracks` занимает `mod.rs:1362–1463`, не `1362–1445`; `load_more_wave_tracks`
  начинается на `manager.rs:1012` (диапазон `1012–1052` верен).
- «WaveEngine вырезает подкасты и длинные разговорные видео» — точнее: окно длительности
  + стоп-слова в тексте; видео без метаданных о длительности (парсер их не всегда достаёт)
  проходят проверку насквозь.
- Block «Запуск Волны (`user:onyourwave`)» — это id Яндекса; для YT Music он просто
  проваливается в последнюю ветку разрешения seed.
- Идея с `params` с тех пор проверена и отклонена: чипы YT Music — это не фильтры,
  а варианты сида (`RDAT…`, см. §5.2). Мульти-сид сделан без новых полей —
  чередованием якорей (§5.3). `FEmusic_radio_*` и `TUNER_CONTROL_SELECTION` в коде
  по-прежнему отсутствуют, ответов с такими полями мы не снимали → **гипотезы**.

## 4. Текущие ограничения (проверено по коду)

Снимок на момент анализа; пункты, закрытые позже, помечены ✅ со ссылкой на §5.

1. **Статичный сид.** ~~Один `RDAMVM`, `last_seed` не меняется → узкий поджанровый пузырь
   после 15–20 треков.~~ ✅ закрыто: seed drift (§5.1) и чередование якорей (§5.3).
2. **Фильтры не влияют.** Ветка `YouTubeMusic` в `load_more_wave_tracks` возвращается
   (`manager.rs:1052`) до чтения `current_mood`/`current_language`/`current_character`;
   значения в состоянии копятся (`apply_rotor_filter`, `manager.rs:1905`, `1939`), но
   уходят только в Яндекс. У YT Music эту роль играют чипы станции из `next` (§5.2):
   они меняют сид, а не подмешивают фильтр.
3. **`seed_artists` — мёртвый груз.** Единственный писатель — `wave_engine.rs:113`
   `add_seed_artist`, вызовов нет нигде в проекте (проверено `grep -rn`). Скоринга по
   любимым артистам не существует.
4. **Истощение continuation — реальная дыра.** ✅ закрыто: §5.4 (один повтор с другим
   якорем, затем честная остановка). ~~Токен пропал/ответ пустой →~~
   `batch_id: None` → следующий refill повторяет *seed*-запрос → те же треки режет
   `dedup_tracks` → очередь перестаёт расти, а ошибки не будет. Никакого «пере-сидирования»
   нет.
5. **История против библиотеки.** Дедуп только по `recent_history` (100) и текущей очереди,
   поэтому трек из «Мне нравится» вернётся после 100 проигрываний. `recent_history`
   набивается при проигрывании, но не при старте станции.

## 5. Точки роста и как их проверять до кода

Правило: сначала снять живой ответ InnerTube в `/tmp` и убедиться, что нужное поле там
есть, и только потом писать код. «Документация» по InnerTube неполная, а поля вроде
`params` меняются между клиентами.

### 5.1 Seed drift — ✅ сделано

- **Что:** каждые `SEED_DRIFT_AFTER_TRACKS = 12` сыгранных треков Волна переезжает на свежий
  сид: `get_station_tracks("track:<текущий трек>", None)`, старый `batch_id` выбрасывается.
- **Где:** `wave_engine.rs` (`played_since_seed`, `seed_drift_due`, `mark_seed_started`),
  `manager.rs` (`plan_wave_fetch`, ветка догрузки YT в `load_more_wave_tracks`).
- **Почему 12:** меньше — дёрганое звучание и лишние запросы, больше — поджанровый пузырь
  успевает сформироваться. Счётчик считает только реально начатые треки и сбрасывается
  при смене станции/фильтра Ротора.
- **Хвост очереди:** свежий батч **заменяет ещё не сыгранный хвост** (`truncate(current_index+1)`),
  иначе очередь росла бы бесконечно и в ней копились бы треки чужого сида. Всё, что уже
  сыграно (включая текущий трек), остаётся — индекс не сдвигается.
- **Проверка (живая, 14 скипов):** `[wave] сид обновлён: track:DJoPdsGMbH8`, очередь
  15 (сыгранное) + 43 (новый сид) = 58, `current_index` не поехал.
- **Риск:** прыжок звучания в момент смены сида. Это осознанный компромисс: переезд
  ставится на границу трека, а не посреди воспроизведения.

### 5.2 Чипы станции из `next` — ✅ сделано (проверено живьём)

- **Что:** YT Music присылает чипы прямо в ответе `next` — `chipCloudChipRenderer` с
  подписями «Все», «Знакомое», «Популярное», «Рекомендованное», «Редкие треки», «Бодрость»,
  «Рок», «Металл», «Трэшкор». У каждого есть `playlistId` вида `RDAT` + тег + сид, например
  `RDATiYvJQt3MFzt8PE`; лежит он не прямо в `navigationEndpoint.watchEndpoint`, а глубже —
  в `navigationEndpoint.queueUpdateCommand.fetchContentsCommand.watchEndpoint` (живой ответ
  2026-11-01), поэтому парсер ищет первый `playlistId` по всему эндпоинту рекурсивно.
- **Ключевое (проверено):** это **не фильтры поверх текущего микса, а варианты его сида.**
  Подмена `playlistId` меняет выдачу: у «Знакомого» с базовым автомиксом совпало
  2 трека из 60, у «Редких треков» — 2 из 73. Поэтому чипы нельзя сделать через `params`:
  старый план на `params` был ошибкой.
- **Где:** парсер `parser/radio.rs::parse_station_chips` (рекурсивный обход, дедуп по
  `playlistId`), `api/provider.rs` (`StationChip`, `StationBatch.chips`),
  `ytmusic/mod.rs` (станция `variant:<playlistId>`), `manager.rs`:
  `apply_station_variant` и событие `PlayerUiEvent::WaveChips`, UI —
  `ui/wave_view.rs::set_chips` (кнопки в карточке настройки волны).
- **Станция `variant:<playlistId>`:** запрос `next` с
  `{"videoId": <последний сид>, "playlistId": <playlistId чипа>}`; если выдача пустая —
  откат на обычный `RDAMVM<сид>`. У «Все» в `playlistId` лежит базовый автомикс
  `RDAMVM<сид>`, то есть выбор чипа равен текущему поведению.
- **Проверка:** живые ответы `next` (цифры выше), живой прогон парсера — 13 чипов из
  одного ответа, юнит-тест `test_parse_station_chips` (включая форму с
  `queueUpdateCommand`).
- **Выбор переживает Seed Drift:** выбранный вариант хранится в состоянии как
  `variant:<playlistId>`, а запрос догрузки собирается как
  `variant:<playlistId>:<якорь>` (`plan_wave_fetch` → `variant_playlist_id`). Без этого
  первый же дрейф (§5.1) уходил в `track:<якорь>`, то есть молча сбрасывал выбранный чип
  на общий автомикс. Явный сид после `variant:` — второй сегмент станции, он же уходит
  в откат `RDAMVM<сид>` внутри `get_station_tracks`.
- **Чипы запрашиваются один раз на станцию:** `PlayerState::wave_chips_station` — ключ
  станции, к которой относится набор (пустой набор = «вариантов нет», отрицательный кэш),
  `wave_chips_pending` — запрос в полёте, чтобы `ensure_wave_chips` на `TrackStarted`
  не дублировал `next`. У выбранного варианта чипы относятся к той же станции, поэтому
  пустой ответ нового варианта не прячет ряд.
- **Подсветка активного варианта:** `PlayerManager::wave_variant_id()` из `station_id`,
  класс `selected` у кнопки (тот же оранжевый `#ff6b4a`, что у выбранного фильтра Ротора).
  `set_chips` хранит последний отрисованный набор и активный id, поэтому ряд не
  пересобирается на каждом треке.
- **Не путать:** `browse FEmusic_moods_and_genres` отдаёт 37 `musicNavigationButtonRenderer`
  с `params` — для трек-радио они не работают (пересечение 50/50, то есть шум).

### 5.3 Мульти-сид (несколько якорей) — ✅ сделано (чередование)

- **Что:** переезды сида (5.1) больше не идут от одного и того же якоря. Каждый второй
  переезд стартует от **дальнего края очереди** — трека, который пришёл из другой порции
  провайдера, — а не от того, что звучит сейчас. Так микс не затягивается в один
  поджанровый пузырь.
- **Где:** `manager.rs` (`pick_drift_anchor`, вызов в догрузке YT-ветки),
  `wave_engine.rs` (`drift_serial`, `note_seed_drift() -> u64`).
- **Правило:** чётный `serial` — текущий трек (или хвост, если текущего нет), нечётный —
  хвост, если он отличается от текущего, иначе текущий. Пустые и пробельные id
  отбрасываются, так что якорь всегда валидный.
- **Проверка:** юнит-тесты `pick_drift_anchor` в `manager.rs`; в логе
  `[wave] переезд #N: сид от <id>`.
- **Чего по-прежнему нет:** `tuning`/`videoIds` с несколькими сидами в одном
  запросе. Такого стабильного контракта у `WEB_REMIX` не нашлось, и он не нужен:
  чередование якорей даёт тот же эффект двумя обычными запросами подряд.

### 5.4 Пере-сидирование при истощении continuation — ✅ сделано (базовый вариант)

- **Что:** если токен продолжения кончился или ответ пришёл пустой (всё отсеялось
  фильтрами), делается **один** повтор с другим якорем — `track:<последний трек очереди>`
  вместо текущего. Без этой ветки очередь молча переставала расти.
- **Где:** `manager.rs`, ветка YT в `load_more_wave_tracks` (`exhausted` → `retry`).
- **Проверка:** юнит-тесты `wave_fetch_tests`; в логе `[wave] продолжение исчерпано — новый сид: …`,
  а если и повтор пуст — `[wave] волна выдохлась: станция «…» не дала новых треков`
  (раньше это был молчаливый `return`).
- **Бюджет:** ровно один повтор. Иначе два пустых ответа подряд превращаются в цикл
  пере-сидирования.
- **Риск:** якорь из хвоста очереди может оказаться треком, который слушатель ещё не слышал —
  тогда новый микс уедет в его сторону. Пока это лучше, чем остановившаяся Волна.

## 6. Чего не делать

- Не тянуть `RDAMVM` с префиксом-`UC` (канальные id) — вернёт не то.
- Не полагаться на длительность из `search_all`: строки без `lengthSeconds` дают
  `duration_ms = None`, и `is_clean_music_track` такие треки пропускает.
- Не менять формат `{"continuation": …}` на `videoId`-запрос при наличии токена: сервер
  ответит первой страницей того же сида, и `dedup_tracks` вырежет всё.
